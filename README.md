# Cardia — 게임을 직접 플레이하는 AI 버추얼 스트리머


실행영상 
https://youtu.be/U5D1IRawTy8?si=WaCFvVPhV9nRT9Yp

로컬 PC에서 **혼자 방송하는 AI**입니다. 사람이 조종하지 않습니다.
LLM이 게임을 직접 플레이하고, 판단 이유를 음성으로 말하고, 시청자 채팅과
후원에 반응하고, 정해진 시간이 되면 스스로 인사하고 방송을 종료합니다.

지원 게임: **Balatro**, **Slay the Spire** (둘 다 화면 인식이 아니라 게임의
상태 API/모드를 통해 플레이합니다)


```
게임 상태(JSON) ──▶ 두뇌(Claude) ──▶ 행동 계획 ──▶ 게임 조작
                        │
                        ├──▶ 대사 ──▶ TTS ──▶ 가상 오디오 케이블 ──▶ OBS
                        ├──▶ 표정 ──▶ 아바타(veadotube)
                        └──▶ 시행착오 기록 ──▶ Obsidian ──▶ 다음 판단에 재주입
```

## 이 프로젝트가 실제로 어려웠던 지점

동작하는 데모를 만드는 것과, **2코어 노트북에서 1시간 40분 동안 사람 개입
없이 버티는 방송**을 만드는 것은 다른 문제였습니다. 아래는 실제로 부딪히고
측정해서 해결한 것들입니다.

### 1. 응답 속도 — 판단 23초 → 5.7초

방송에서 20초 정적은 치명적입니다. 프롬프트와 모델을 아무리 손봐도 나아지지
않아서, 호출 하나를 분해해 측정했습니다.

| | 시간 |
|---|---|
| 모델이 실제로 생각한 시간 | 3.7 ~ 10.5초 |
| CLI 프로세스를 띄웠다 죽이는 시간 | **8 ~ 46초** |

전체의 60~85%가 판단이 아니라 **프로세스 부팅**이었습니다. 매 판단마다 새
프로세스를 띄우는 구조가 저사양 CPU에서 병목이었던 것입니다.

해결: 프로세스를 살려두고 재사용(`--input-format stream-json`). 함정이 둘
있었습니다 — CLI가 stdin을 3초만 기다려서 미리 띄워둘 수 없었고, 대화가
누적되어 5턴 만에 컨텍스트가 10.8k→34k 토큰으로 불어나며 모델이 이전 턴
얘기를 하기 시작했습니다. 판단마다 `/clear`를 넣어 컨텍스트를 고정했습니다.

**실측(방송 부하 상태): 중앙값 23.2초 → 5.7초, 프로세스 오버헤드 16.7초 → 2.1초**

부수적으로 발견한 것 하나 — 히든 씽킹 512토큰은 상점 판단에서 **2배 느리고
결과도 나빴습니다**(22.4초/화면 미완결 vs 10.1초/한 번에 완결). 직관과 반대라
A/B로 확인하지 않았으면 계속 켜두었을 것입니다.

### 2. AI가 상점에서 아무것도 사지 않던 문제

게임 API가 주는 카드 데이터 구조를 잘못 읽고 있었습니다. 효과 설명이
`value.effect`에 있는데 최상위 `effect`를 보고 있어서, AI 눈에 보이는
상점은 이랬습니다:

```json
{"name": "Cavendish", "buy": 8}
```

**이름과 가격뿐, 무슨 카드인지가 없었습니다.** 살 수가 없는 게 당연했습니다.
같은 이유로 바우처와 부스터팩은 아예 목록에서 빠져 있었습니다.

수정 후에는 세 종류의 상점 진열을 비교해서 삽니다. 한 줄만 고르는 편향이
생기지 않았는지 **정답이 매번 다른 상점 3개**로 검증했습니다 (3/3 정답).

### 3. 학습이 오히려 AI를 멍청하게 만들던 문제

시행착오를 Obsidian에 쌓고 다시 읽는 구조인데, 볼트를 열어보니 이런 게
쌓여 있었습니다:

> "Ante 1 Small Blind가 최대 killer다"

Small Blind는 이 게임에서 제일 쉬운 관문입니다. 원인은 죽은 관문의 종류를
기록하지 않아서, 빈 보드로 첫 관문에 죽은 것을 전부 "보스에게 패배"로
분류한 것이었습니다. 이 잘못된 노트가 **매 판단마다 주입**되고 있었습니다.

고친 것:

- 진짜 보스 관문만 기록 (종류를 상태에서 읽어 판별)
- 배울 게 없는 판(조커 0·레벨업 0)은 교훈을 아예 건드리지 않음
- 증류 프롬프트를 "**지우는 게 추가하는 것만큼 가치 있다**"로 재작성 —
  한 번의 패배는 일반 규칙의 근거가 아니고, 게임 메커니즘과 모순되면 삭제
- 무한 증식 차단: 교훈 10줄 / 플레이북 35줄 / 관문 노트 8건 / 리포트 30개,
  전부 코드에서 강제

실측: 오염된 노트를 넣었더니 10줄 → 6줄로 **가지치기**하고 잘못된 내용을
전부 삭제했습니다.

### 4. 조언이 효과 있었는지 아무도 검증하지 않던 문제

위 3번을 고쳐도 남는 문제가 있었습니다 — **그럴듯하게 들리는 해로운 규칙은
계속 살아남습니다.** 측정하는 장치가 없으니까요.

그래서 판이 끝날 때마다 **그 판 동안 적용 중이던 교훈 버전**으로 태그해
성적을 기록하고, 다음 증류 때 비교를 증거로 넘깁니다:

```
current rules (r3): 3 runs, best ante 1, average 1.0
previous rules (r2): 3 runs, best ante 4, average 3.3

YOUR LAST REVISION MADE THINGS WORSE. 지난번 바꾼 걸 되돌리거나 교체하라,
위에 한 줄 더 얹지 말라.
```

양쪽 표본 2판 이상 + 평균 0.3안테 이상 차이일 때만 판정해서 운으로 흔들리지
않게 했습니다.

### 5. 무인 운영 — 사람이 없어도 깨지지 않기

방송 중에 사람이 개입하거나 뭔가 죽어도 조용히 끝나야 합니다.

- 게임이 60초 이상 응답 없으면 → 죽은 화면을 계속 송출하지 않고 정상 종료
  (종료 멘트 → OBS 방송중단 → 게임 저장 종료 → 아바타 → 자신)
- 루프가 예외로 죽으면 자동 재시작(5회), 그 이상이면 정상 종료
- 강제 종료로 남은 헬퍼 프로세스는 **다음 실행 때 청소** (매칭 조건을 좁혀
  사용자의 다른 프로세스는 절대 건드리지 않음)
- 게임이 수를 거부하면 거부 사유를 기억에 넣고 재판단 → 3회면 안전한 수 →
  6회면 그 판을 포기하고 새 판 (판 하나 버리는 게 방송 전체가 죽는 것보다 낫다)

## 판단 비용을 줄인 방법

LLM 호출 하나가 5초라면, 호출 수를 줄이는 게 곧 속도입니다.
**선택지가 하나뿐인 화면은 아예 묻지 않습니다.**

| 화면 | 처리 |
|---|---|
| 라운드 정산 | 즉시 (선택지 없음) |
| 관문 선택 | 즉시 (진행용 클릭) |
| 돈이 모자라 아무것도 못 사는 상점 | 즉시 나감 |
| 카드 플레이 / 상점 구매 / 팩 선택 | **AI 판단** |

한 안테(11화면) 기준 브레인 호출이 **11회 → 5회**로 줄었습니다.
판단이 필요한 곳은 그대로 두고, 기계적인 클릭만 걷어낸 것입니다.

모델도 상황에 따라 나눕니다 — 판을 좌우하는 화면(상점·팩 선택)은 상위 모델,
반복되는 손패 판단은 빠른 모델. 실패가 누적되면 자동으로 낮춥니다.

## 구조

```
orchestrator.py     메인 루프. 우선순위 큐(후원>채팅>잡담), 게임 루프 2종,
                    종료 시퀀스, 안전장치
brain.py            LLM 호출 계층. 라우팅, 웜 프로세스 재사용, 재시도,
                    타임아웃 시 모델 강등
balatro_link.py     Balatro JSON-RPC 클라이언트 + 상태 압축(13,648자 → 842자)
balatro_profile.py  세이브 파일을 직접 읽어 해금된 덱/난이도 판별
avatar_state.py     아바타 표정 전환 (게임 상황에 따라)
safety.py           채팅 필터 2단계 (규칙 → 분류 모델)
tts.py              음성 합성 → 가상 오디오 케이블
twitch_chat.py      트위치 채팅 (익명 IRC)
youtube_chat.py     유튜브 채팅·슈퍼챗 (API 키 불필요)
prompts/            역할별 프롬프트
config/models.yaml  모델 라우팅 설정
tools/              검증 스크립트 45종 (아래)
```

### 검증을 코드로 남긴 이유

방송 중에는 디버깅할 수 없습니다. 그래서 고친 것마다 **그 고침이 유효한지
다시 물어볼 수 있는 스크립트**를 남겼습니다.

```bash
python tools/latency_report.py       판단 지연을 warm/cold로 분리 집계
python tools/check_shop_rows.py      상점 세 줄 중 맞는 걸 고르는지 (편향 검사)
python tools/check_learning_loop.py  잘못된 데이터가 볼트에 쌓이지 않는지
python tools/check_feedback_loop.py  교훈이 성적으로 심판받는지
python tools/check_manual_kill.py    강제 종료 시 안 꼬이는지
python tools/sim_balatro_loop.py     게임 없이 루프 전체를 드라이런
```

`sim_balatro_loop.py`는 게임을 켜지 않고 가짜 게임으로 루프를 돌려, 어떤
화면이 브레인을 부르고 어떤 화면이 즉답되는지, 거부당했을 때 멈추지 않는지를
확인합니다. 실제로 이 시뮬레이터가 **화면이 안 바뀌면 영원히 대기하는
데드락**을 잡아냈습니다.

## 기술 스택

| | |
|---|---|
| 언어 | Python 3.12 |
| LLM | Claude (헤드리스 CLI, 역할별 모델 라우팅) |
| 게임 연동 | Balatro: balatrobot(JSON-RPC) + Steamodded / StS: CommunicationMod(stdin-stdout) |
| 음성 | Piper TTS (로컬) → VB-Audio Virtual Cable |
| 아바타 | veadotube mini (웹소켓으로 표정 제어) |
| 방송 | OBS Studio (QSV 하드웨어 인코딩, obs-websocket으로 제어) |
| 지식 저장 | Obsidian (마크다운 + 위키링크) |
| 실행 환경 | Intel Celeron 6305 (2코어) / 내장그래픽 / 16GB |

저사양이 제약이 아니라 **설계 조건**이었습니다. 3D 아바타나 로컬 LLM은
처음부터 배제하고, GPU는 인코딩에만 쓰고, CPU 경합을 피하려고 음성 생성과
게임 판단을 서로 양보하게 만들었습니다.

## 실행

```bash
cp .env.example .env      # 채널명, 볼트 경로 설정
```

스트림 키는 이 저장소나 `.env`에 넣지 않습니다. **OBS에만** 입력합니다.

```bash
balatro유튜브방송시작.bat   # Balatro → 유튜브
방송시작.bat                # Slay the Spire → 트위치
balatro리허설시작.bat       # 송출 없이 로컬 녹화만 (테스트용)
```

런처가 아바타 → OBS → 게임 → AI 순으로 띄웁니다. 순서에 이유가 있습니다 —
OBS는 CPU가 한가할 때 켜야 하드웨어 인코더를 잡고, AI는 게임이 로딩되는
동안 미리 워밍업해야 첫 판단이 즉시 나옵니다.

## 알려진 한계

정직하게 적습니다.

- **교훈의 옳고 그름은 모델 판단입니다.** 성적 피드백으로 압박은 하지만
  보장은 아닙니다.
- **AI가 자기 나쁜 수에 붙인 그럴듯한 이유가 다시 학습 재료가 됩니다.**
  구조적 한계라 필터로 막히지 않습니다.
- 유튜브 라이브 자동 시작은 유튜브 스튜디오 쪽 설정에 의존합니다.
- 실행 환경이 특정 PC에 맞춰져 있습니다(경로 하드코딩). 이식성보다 이
  하드웨어에서 확실히 도는 것을 우선했습니다.

## 이 저장소에 없는 것

- **스트림 키·비밀번호** — 절대 커밋하지 않습니다
- **서드파티 바이너리** (OBS, veadotube, Piper, 약 1.8GB) — 직접 받는 것들
- **아바타 이미지·방송 녹화본·로그** — 프로젝트 결과물이 아닌 산출물
